# GoF 设计模式仓库 · 项目规范

本仓库基于 `.NET 10` / `C# 14` 实现 GoF 23 种设计模式，每个模式是一个**独立子目录**，均可单独构建运行。

本文规定了本仓库中代码示例与文档的编写规则，改写任何模式前先通读。改完必须保证项目可构建、可运行。

**SDK 说明**：本机默认 `dotnet`（PATH）为 8.0.100，仅支持 net8.0；**canonical 命令是 `~/.dotnet/dotnet`（SDK 10.0.400，含 9.0.304）**。所有构建/运行统一用它。

---

## 一、📁 项目结构规则

- 每个模式一个独立目录，命名为 `<模式名>Pattern/`（如 `StrategyPattern/`、`ObserverPattern/`）。
- 目录内至少包含：`README.md`、`Program.cs`、`<模式名>Pattern.csproj` 及场景子目录。
- `.csproj` 的 `TargetFramework` 必须为 **`net10.0`**，不得更改、不得回退 net8.0。`ImplicitUsings` / `Nullable` 保持 enable。
- **示例代码按场景分子目录**，一个场景一个文件夹，以**场景名**命名（如 `Restaurant/`、`TextEditor/`、`FileSystem/`），该场景的全部角色（接口、具体实现、上下文、接收者）同放该文件夹下。
- **命名空间平铺**：全部文件统一 `namespace <模式名>Pattern;`，场景子目录**不**引入命名空间层级（禁止 `CommandPattern.Restaurant` 这类写法）。
- **示例必须自成体系**：即使不同示例的辅助代码结构相同，也必须各自复制一份到自己的目录，**不得抽取公共文件共享**。每个示例都能独立读懂、独立演示。
- `Program.cs` 为演示入口：依次运行各场景示例，输出与 README「运行结果」保持一致。
- **旧写法对比（Legacy/switch 版）不单独建目录**：与传统写法的对比以精简代码块形式并入 README 对比节，代码目录只保留模式实现。
- 验证命令：
  - 单模式：`~/.dotnet/dotnet run --project <模式名>Pattern`
  - 整库：`~/.dotnet/dotnet build DesignPatterns.slnx`（.NET 10 SDK 支持 slnx 格式，须 0 警告 0 错误）

## 二、💻 代码规则

- 使用**文件作用域命名空间**（`namespace XxxPattern;`），按上文平铺规则。
- 关键位置（类、核心方法）写**中文注释**，说明职责/场景；其余代码不加冗余注释。
- 模式代码遵循经典结构（泛化表述，适配各类模式）：
  - 抽象契约定义接口（`IStrategy`、`ICommand`、`IState`、抽象类或接口均可）
  - 多个具体实现类
  - 持有抽象引用的角色（上下文/调用者/代理）通过统一入口委托或切换
- **现代语法优先**（能用新语法就不用旧写法）：
  - **主构造函数**绑定依赖：`class Department(string name) : IOrgUnit`、`class NoQuarterState(GumballMachine machine) : IState`，替代手写构造函数赋值
  - **集合表达式** `[...]` / `[..x]`：`ICommand[] partyOn = [new LightOnCommand(light)]`、`private readonly List<MenuComponent> _components = [];`
  - **`is null` / `is not null`** 模式替代 `== null` / `!= null`；`is` 类型模式替代 `as` + 判空
  - **target-typed new**：`new()`（如 `new(() => new Singleton())`、`_lock = new()`）
  - **`System.Threading.Lock`**（.NET 9+）替代 `object _lock`；lock 对象场景一律用它
  - **`field` 关键字**（C# 14）：属性需要自定义访问器逻辑又要保留自动属性简洁性时使用（如 `int Count { get => field; set => field = Math.Max(0, value); }`）
  - **`params` 集合**（C# 13）：可声明 `params ReadOnlySpan<T>`，按需使用
  - `Random.Shared` 获取线程安全随机数（演示输出仍须确定性，见下）
  - 字符串插值内直接用表达式；简单单行逻辑用 `=>` 表达式主体
- 类名避免与 BCL 冲突：如 `File`/`Folder` 会与 `System.IO` 产生 CS0104 二义性，应命名 `FileNode`/`FolderNode`。
- **输出确定性**：演示输出不得含随机（如糖果机按概率中奖）、时间戳等不确定内容，保证 README 可精确回填、多次运行结果一致；确需动态值（如日志文件名带时间）时 README 贴代表性示意值即可。
- 场景调用要贴合现实常识（如路线规划传入真实距离、时间），避免明显不合理的数据。
- 输出风格：开场「=== 模式名 ===」标题 + 描述句；演示过程中用 `>>` 标注即将发生的动作；类输出用 `[标签]` 前缀（`[初始化]`/`[拒绝]`/`[出货]`/`[已完成]`）标注结果类别——输出即文档，无注释也可读懂。
- **不写未被消费的代码**：未被调用的包装类（如多余的 Client 类）、未输出的属性一律删除。

## 三、🎯 示例规则

- **示例必须经典、常见、易理解**：优先采用实际开发/生活场景（排序、支付、餐厅点餐、文件系统、组织架构、电商订单等），拒绝 Duck/Animal/Shape 等抽象教学类；HFDP 经典案例（糖果机）足够直观的可保留。
- **示例数量按需**：模式本身经典且一个示例即可讲清（或存在天然的最佳单一场景，如外观模式的家庭影院）时，一个示例即可，不必凑数；多示例必须有区分度，不得同质化——
  - 策略模式三例：排序策略（算法替换）、支付方式（接口切换）、路线规划（带参数的组合）。
  - 观察者模式三例：气象站（推模型+退订）、股票行情（订阅过滤）、公众号（退订后不再接收）。
  - 命令模式三例：餐厅点餐（命令排队）、智能家居（撤销+宏命令）、文本编辑器（双栈撤销/重做）。
  - 单例模式三例：日志记录器（懒汉式 `Lazy<T>`）、配置管理器（饿汉式）、办公室打印机（生活场景）。
  - 状态模式两例：糖果机（同一动作在不同状态下结果不同）、电商订单（状态流转+非法操作拦截）。
  - 组合模式两例：文件系统（透明式）、组织架构（安全式）。
- **变体即示例**：模式有多种实现变体（单例的懒汉/饿汉/DCL、组合的透明/安全）时，用不同场景示例分别承载，README 中的变体对比表与具体示例小节互相引用。若单一示例已足够经典直观（如外观模式的家庭影院），变体可只在 README 对比节说明、不另立代码示例。
- **优先从 .NET 生态取材**：仅当模式有对应内置接口时（如观察者用 `IObservable<T>`/`IObserver<T>`、退订用 `IDisposable`）。
- **数据要符合客观实情**：城市距离、金额、文件大小等需真实合理。

## 四、📝 文档规则

README 采用**四段式结构**：

```md
# 模式名（中文名 English Pattern）

[TOC]

## 一、📖 概述          — 模式定义、核心思想
## 二、🧩 模式解析      — 类关系图 + 角色表 + 核心代码 + 关键解析
## 三、💻 代码示例      — 每个场景：Mermaid 流程图 + 「角色/文件」表 + 运行结果
## 四、📝 小结          — 核心思想、关键角色、注意事项
```

「模式解析」的骨架（编号按实际内容顺延）：

1. **2.1 类关系图必须是通用图示**（Subject/Observer、Command/Invoker 等抽象角色），用于宏观讲解，**不得直接使用某个具体示例的类**（如 WeatherSupplier）。
2. 若模式有多种**应用形态或实现变体**，紧随其后加对比表（命令的「三类应用」、单例的「三种实现」、组合的「透明 vs 安全」）。
3. **核心代码**：以精简伪代码呈现模式骨架（不含具体业务名）；多种实现变体给多段伪代码（单例：懒汉/饿汉/DCL 三段）；伪代码同样采用现代语法（`Lock`、`is null`、主构造函数风格）；末尾用 `>` 引用块写一句协作方式。
4. **关键解析**：模式的关键机制与易混淆点；「与传统写法对比」（状态 vs switch）、「与相邻模式对比」（状态/命令 vs 策略）以表格并入本节，不再单开章节。

Mermaid 图表布局（**横竖结合，紧凑优先**）：

- 默认横向：类图 `direction LR`、流程图 `flowchart LR`，主链横排；分支/副路径（历史栈、撤销路径）从主链节点分出，自动折到下一行，形成 3~4 列 × 2 行的紧凑形态。
- **避免两个极端**：5+ 节点排成单行（横向滚动）或排成单列（纵向冗长拉长文档）。
- 纯入口节点（`PushUndo()`、Ctrl+Z 等）折叠为箭头标签，减少节点数。
- 纯线性长链用 subgraph 分带：整体 `TB`、带内 `direction LR`、带间一条连线（子图间只连簇级节点，避开子图方向失效的已知问题）。
- 图选型：状态流转用 `stateDiagram-v2`（`direction LR`，终结态用 `[*]`）；树形结构（组合模式）用 flowchart LR——横向层级 + 纵向扇出。
- 配色语义固定（流程图）：蓝 `#4A90D9` 客户端/入口、橙 `#E67E22` 核心角色（上下文/代理/组合节点）、紫 `#7B68EE` 中间机制（命令/栈/队列）、绿 `#27AE60` 末端执行/结果、红 `#E74C3C` 拒绝/失败、灰 `#95A5A6` 终态。

其他细则：

- `[TOC]` 必须保留；章节用「一、二、三、四」中文序号 + emoji 图标。
- 每个代码示例子节结构固定：`> 场景：…` 说明 → Mermaid 流程图 →「角色 | 文件」表格（用相对链接指向真实文件）。
- **三.x 运行结果**：贴出 `dotnet run` 的真实输出（`bash` 代码块），与 Program.cs 一致。
- 小结后不加多余章节。

## 五、✅ 完成标准

1. `~/.dotnet/dotnet run --project <模式名>Pattern` 构建无警告无错误。
2. 输出与 README「运行结果」完全一致，且**多次运行结果确定**（无随机/时间戳漂移）。
3. README 内所有文件链接真实存在、目录路径正确。
4. 遵循「示例自包含」原则：无跨目录共享代码。
5. 图表符合紧凑布局规则与配色语义。
6. `.csproj` 保持 `net10.0`，代码符合「现代语法优先」清单。
